## 一句话结论

Digital Marketing Pro 不是新的营销模型，也不是免配置的营销 SaaS。它把营销机构的 SOP 编排为 **Skill 文档、角色提示、确定性 Python 工具、品牌状态文件、质量门禁和可选连接器**，让 Claude、Codex、Cursor 等宿主 Agent 按固定流程完成营销研究与交付。

更直白地说：它先给宿主 Agent 一张“营销项目地图”，再给地图中每个动作配一份专业作业指导书。用户仍然是最终决策者，宿主模型负责理解与推理，这个仓库负责提供营销项目总监式的拆解方法、执行规范和检查机制。

## 背景：它要解决什么问题

通用大模型会写文案、做分析，也能提出营销建议，但单次回答通常存在四个工程问题：

1. **容易跳步**：模型可能直接写广告，却没有先确认产品事实、目标客户、定位和预算。
2. **难以复用**：同一团队在不同会话、不同模型或不同客户上得到的流程不一致。
3. **状态易丢失**：品牌事实、客户确认、中间产物和长任务进度难以稳定传递。
4. **执行风险高**：生成建议与真实发布、投放、发信之间缺少审批、权限和审计边界。

Digital Marketing Pro 的背景不是“再训练一个更懂营销的模型”，而是把营销机构积累的流程知识工程化：把何时触发、需要什么输入、先做什么、产出什么、交给谁、怎样检查以及何时必须由人批准，写成宿主 Agent 可以读取的 Skill 和状态协议。

## 核心工作方式：先拆解，再指导动作

```text
业务问题
  ↓
宏观流程 / engagement 命令识别阶段与依赖
  ↓
选择品牌、研究、内容、SEO、广告、分析等专业 Skill
  ↓
每个 Skill 规定输入、步骤、产物、质量检查与下一步交接
  ↓
需要稳定计算或状态操作时运行 Python 工具
  ↓
人工确认关键事实与高风险动作
  ↓
连接器在获得授权后执行真实平台操作
```

例如“为新的 AI 办公产品制定并执行营销方案”，宏观层会先拆成品牌建档、用户与竞品研究、定位、内容与渠道、广告、发布和复盘；进入“竞品研究”动作后，再使用竞品研究 Skill 指导收集字段、比较方法和报告格式；其输出随后成为定位 Skill 的输入。它因此形成“总流程 → 专业动作 → 工具与检查 → 下游交接”的递进链路。

需要特别注意：仓库自身是静态方法库，不会脱离宿主模型主动思考。真正的选择和推理由宿主 Agent 完成；163 个 Skill 提供可选择的工作协议，其中一部分有 Python 脚本支撑，一部分主要是结构化指导。

- 当前网络安全策略拦截了 NLTK 可选语料的在线下载；上游回退路径仍使测试全部完成。因而这一结果证明锁定源码的软件契约可运行，不代表可选语料或任何第三方营销平台已经连通。

## 它怎样工作

```text
用户需求
  ↓
宿主模型根据 SKILL.md 描述选择能力
  ↓
读取品牌 profile / Living Instruction File / 上游产物
  ↓
按 Skill 流程生成、研究或调用确定性 Python 脚本
  ↓
保存品牌状态、工件和长任务 checkpoint
  ↓
质量门禁与人工验证
  ↓
需要真实写操作时，生成连接器请求并等待审批
```

开放式判断、研究和文案生成仍由宿主大模型完成；仓库本身不包含基础模型。`agents/*.md` 是角色规范，不是 24 个常驻进程。外部连接器默认不自动启用，真实数据质量取决于用户连接的 CRM、广告、分析、邮件或 CMS 系统。

## 代表性使用场景

1. **新客户营销咨询**：品牌建档、Stone vs Opinion 信息分层、外部研究、四份核心文档、客户验证、增长计划与渠道策略。
2. **内容发布流水线**：内容简报、写作、事实/声明检查、品牌语气、SEO、人工确认与 CMS 发布准备。
3. **SEO / AEO / GEO**：技术 SEO、关键词聚类、页面审计、AI 搜索可见性和竞品追踪。
4. **广告与自动化**：预算与媒介计划、广告创意、平台请求 manifest、审批、连接器执行和日志。
5. **经营复盘**：归因、ROI、异常、漏斗、队列、流失风险、客户报告和 agency dashboard。

## 能力分层

| 层级 | 主要能力 | 作用 |
| --- | --- | --- |
| 项目编排层 | 完整 engagement、阶段顺序、前置依赖、checkpoint | 把宏观问题变成可推进的项目 |
| 专业方法层 | 品牌、研究、内容、SEO/AEO、广告、CRM、分析 Skill | 指导每个具体动作怎样完成 |
| 角色规范层 | 24 份 Agent 角色文档 | 约束战略、品牌、内容、搜索和分析等岗位视角 |
| 确定性工具层 | 93 个 Python 脚本 | 完成评分、计算、验证、状态和请求生成 |
| 状态与知识层 | 品牌 profile、Living Instruction File、中间工件 | 保持跨阶段和跨会话的一致性 |
| 治理层 | 质量门禁、人工确认、审批状态和日志 | 阻止未经验证或未经授权的动作继续执行 |
| 集成层 | 可选 API、MCP 与平台连接器 | 在权限允许时连接 CRM、CMS、广告、邮件和分析系统 |

## 真实边界

- 没有品牌资料、业务数据和连接器时，输出主要来自通用知识、用户输入和模板化流程。
- 402 个软件测试验证的是状态与契约正确性，不能证明营销策略提高了收入、排名或转化率。
- `approval-manager.py` 是本地 JSON 状态机，不等同于企业身份、RBAC、双人复核或不可抵赖审计。
- “EU AI Act Article 50 ready”是上游项目的产品声明，不是监管机构或律师的认证意见。
- AEO/GEO 探测、真实发布、广告创建和邮件发送需要 API、MCP、密钥、平台权限及额外审查。
- README 中的时间、成本和业务效率数字尚未看到独立、可重复的对照实验。

## 研究价值

该项目作为 **Agent 工程样本** 的价值高于作为“营销效果已验证系统”的价值。推荐继续研究：

- 163 个 Skill 的路由准确率、冲突率和上下文成本；
- Skill 文档与确定性脚本的职责边界；
- checkpoint、品牌隔离和跨会话状态的一致性；
- 人工审批是否真的能阻止误发、误投和越权操作；
- 去掉品牌上下文、脚本或质量门禁后的消融结果；
- 与单 Prompt、通用 Agent、营销专家的盲评与真实业务指标比较。

## 扩展方向：怎样从方法库走向可验证系统

### 1. 建立真正的总控编排器

把 Skill 的前置条件、输入输出、风险等级和交接关系整理为机器可读的有向图。总控层根据用户目标生成任务树，明确哪些任务可以并行、哪些必须等待事实确认，并展示当前阶段、缺失输入和下一步动作。这样才能把“像营销总监一样指导”从提示约定升级为可观察的运行时能力。

### 2. 建立 Skill 路由评测

为真实营销请求建立带标准答案的数据集，衡量应该选择哪些 Skill、是否漏选、是否冲突、路由成本和最终完成率。需要同时设置单 Prompt、通用 Agent 和人工营销专家基线，避免只用仓库自己的测试证明仓库有效。

### 3. 强化长期状态与品牌隔离

将品牌事实、观点、客户确认、内容版本和实验结果存入有模式约束的数据库；增加租户隔离、版本迁移、来源引用和过期策略。关键事实应能追溯到原始证据，并明确哪些结论只是模型推断。

### 4. 把本地审批升级为企业治理

在真实执行前接入身份认证、RBAC、双人复核、预算上限、幂等键、不可篡改审计和回滚策略。发布、投放、批量发信等动作需要预览差异、精确权限和可撤销窗口，不能只依赖本地 JSON 状态。

### 5. 建立受控连接器层

为 CMS、广告平台、CRM、邮件与分析系统设计统一 manifest：先生成计划和预览，再由审批服务签发短时权限，连接器执行后保存平台响应。读取、草稿、发布和资金操作应使用不同权限等级。

### 6. 建立营销效果实验

软件测试只能证明代码契约。要证明业务价值，需要对真实客户或仿真数据开展 A/B 测试，观察完成时间、返工率、事实错误率、品牌一致性、获客成本、转化率和收入，并记录模型、提示、数据和人工投入成本。

### 7. 迁移到其他专业领域

它的“总流程 → 专业 Skill → 确定性工具 → 状态 → 审批”结构可以迁移到产品研究、投资研究、内容生产、软件交付和企业咨询。迁移时应复用编排与治理框架，而不是照搬营销术语和未经验证的业务声明。
